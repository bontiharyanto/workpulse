# ADR-0016 — Multi-tenant SUPER_ADMIN Company CRUD + Structured Observability

**Status:** Accepted — 2026-08-02
**Related:** ADR-0014 (mustChangePassword), `apps/api/src/company-admin/**`, `apps/api/src/observability/**`

---

## Context

Workpulse has always been _multi-tenant capable_ at the schema layer — every
row carries a `companyId`, every guard forces isolation on it. What was
missing was the operational tooling to actually manage those tenants:

1. **No CRUD for `Company`.** The only tenant that existed in production was
   whatever the Prisma seed created at bootstrap. Onboarding a new tenant
   required either editing the seed and running it, or hand-crafting SQL.
   Neither is safe for real customers.

2. **Console-noise logging.** The default Nest `Logger` writes free-form
   text to stdout. It cannot be parsed by a log aggregator (Datadog, Loki,
   CloudWatch), cannot redact secrets by convention, and cannot correlate a
   request across multiple log lines because it has no request id.

3. **No error visibility.** A 500 from a background job or a misfired guard
   surfaced only in whichever terminal was tailing the API — nowhere else.
   On-call had no way to know something broke before customers complained.

Fase 29a addresses (1) and (2)+(3) together because they share dependencies
(env schema, JWT strategy) and are cheaper to review as one shipment.

## Decision

### 1. `CompanyAdminModule` — SUPER_ADMIN cross-tenant CRUD

New module at `apps/api/src/company-admin/`, mounted under `/admin/companies`
(plural). Deliberately **separate from** the existing `/admin/company`
(singular) which is tenant-scoped and open to HR:

| Path                                  | Role gate                   | Scope            |
| ------------------------------------- | --------------------------- | ---------------- |
| `/admin/company` (singular)           | `HR_MANAGER`, `SUPER_ADMIN` | Own tenant only  |
| `/admin/companies` (plural, this ADR) | `SUPER_ADMIN` only          | **Cross-tenant** |

Distinct paths make it impossible for a mis-configured guard to fall from
one to the other — the URL itself encodes intent.

Endpoints:

| Method   | Path                           | Effect                                                          |
| -------- | ------------------------------ | --------------------------------------------------------------- |
| `POST`   | `/admin/companies`             | Create tenant + bootstrap (see §2). Returns temp password once. |
| `GET`    | `/admin/companies`             | List, offset-paginated, search on `name`/`slug`.                |
| `GET`    | `/admin/companies/:id`         | Detail with `userCount` + `departmentCount`.                    |
| `PATCH`  | `/admin/companies/:id`         | Update `name`/`slug`/`timezone`. Slug uniqueness re-checked.    |
| `DELETE` | `/admin/companies/:id`         | Soft-delete. Refuses when active users remain.                  |
| `POST`   | `/admin/companies/:id/restore` | Restore a soft-deleted tenant.                                  |

### 2. Bootstrap transaction

`POST /admin/companies` runs a single `prisma.$transaction` that:

1. Creates the `Company` row (defaults for overtime multipliers, absent-scan
   grace hours, etc. come from the schema).
2. Seeds three baseline `LeaveType` rows: `ANNUAL`, `SICK`, `PERSONAL` (quotas
   `12`, `14`, `3` — HR can adjust).
3. Creates the initial `HR_MANAGER` user with `mustChangePassword=true`.
4. Seeds `LeaveBalance` rows for the HR user against the year of creation.
5. Writes an `AuditLog` entry keyed to the **actor's own tenant**
   (`actor.companyId`) — this is deliberate so every cross-tenant admin
   action appears in the operator's own timeline, which is where the audit
   viewer queries.

A failure at any step rolls the whole thing back — the new tenant either
exists fully usable or does not exist at all. No half-configured tenant
can leak past the API.

The temporary password is generated by `generateTempPassword(14)` (curated
crypto-secure alphabet, no visually confusable characters) and returned
**once** in the HTTP response — never persisted plaintext. The operator is
expected to hand it to the tenant's HR through an out-of-band channel.

### 3. Guardrails

- **Slug uniqueness.** Explicit slug → 409 `SLUG_ALREADY_TAKEN` if taken.
  Omitted slug → derived from name via `derivateSlug()`, then bumped
  (`-2`, `-3`, …) via `uniqueSlug()` until free. Bounded to 100 attempts.
- **HR email uniqueness.** Pre-checked before the transaction so callers
  see a clean 409 `EMAIL_ALREADY_TAKEN` rather than the raw P2002.
- **Timezone.** Validated via `Intl.DateTimeFormat` before the transaction.
- **Self-delete refused.** SUPER_ADMIN cannot soft-delete its own tenant
  (would immediately brick the caller's session). Returns 403
  `CANNOT_DELETE_OWN_TENANT`.
- **Active-user gate.** Soft-delete refuses with 409 `COMPANY_HAS_ACTIVE_USERS`
  when non-deleted users remain. Operator must deactivate them first via
  `/admin/users`. This prevents silent lockouts.

### 4. Structured logging via `nestjs-pino`

Replaces `LoggerModule` bootstrap in `app.module.ts` and swaps
`app.useLogger(app.get(Logger))` in `main.ts`. Behaviour:

- **JSON lines** in production; `pino-pretty` in dev (toggle via
  `LOG_PRETTY=true`).
- **`requestId`** injected from `X-Request-Id` header (if present) or
  freshly generated UUID. Echoed back on the response so client-side
  correlation is possible.
- **`userId`, `companyId`, `role`** attached automatically to every log
  line once `JwtAuthGuard` has populated `req.user`.
- **Redaction** at serialization time for:
  - `req.headers.authorization`
  - `req.headers.cookie`, `req.headers['set-cookie']`, `res.headers['set-cookie']`
  - `req.body.password`, `req.body.currentPassword`, `req.body.newPassword`
  - `req.body.refreshToken`, `req.body.token`
  - `*.password`, `*.currentPassword`, `*.newPassword`, `*.refreshToken`

Redaction is verified by the E2E suite — every observed log line during
the 100-test run showed `"authorization":"[REDACTED]"` and
`"set-cookie":"[REDACTED]"`.

The old `LoggingInterceptor` is deleted; pino-http emits an equivalent
per-request log with the correct level (`error` for 5xx, `warn` for 4xx,
`info` for 2xx/3xx).

### 5. Sentry via `@sentry/nestjs`

Loaded from `src/instrument.ts` — imported as the **very first line** of
`main.ts` so Sentry's OpenTelemetry instrumentation can wrap Node internals
(http, express, prisma) before those modules are required elsewhere.

- **Gated by `SENTRY_DSN`.** Empty DSN → `Sentry.init()` is skipped, all
  subsequent SDK calls become no-ops. This keeps dev + CI environments free
  of accidental captures.
- **User tagging in `JwtStrategy.validate`.** Every request that
  authenticates tags the current Sentry scope with `id`, `email`,
  `companyId`, `role`. Scope is per-request (NestJS integration + Node
  AsyncLocalStorage) — no cross-request leakage.
- **4xx dropped** via `beforeSend`. Validation errors and permission
  denials are business signal, not on-call noise.
- **`AllExceptionsFilter` calls `Sentry.captureException`** for any
  unhandled non-HttpException. `HttpException` still routes through
  `HttpExceptionFilter` and is _not_ captured (matches the beforeSend
  filter).
- Optional performance tracing controlled by `SENTRY_TRACES_SAMPLE_RATE`
  (default 0).

### 6. Env surface

Added to `env.validation.ts` (validated at boot):

```ts
LOG_LEVEL: 'trace' | 'debug' | 'info' | 'warn' | 'error' | 'fatal'; // default: info
LOG_PRETTY: 'true' | 'false'; // default: false
SENTRY_DSN: string | undefined;
SENTRY_ENVIRONMENT: string | undefined; // defaults to NODE_ENV
SENTRY_RELEASE: string | undefined; // typically git SHA
SENTRY_TRACES_SAMPLE_RATE: number; // 0..1, default 0
```

All optional — the API boots identically to before when none are set.

## Consequences

### Positive

- **Onboarding is now self-service for the platform operator.** A new
  customer becomes a working tenant with one API call. No SQL, no seed
  edits.
- **Every log line is correlatable + safe.** `requestId` threads through
  filters, services, and Prisma; secrets never leave stdout.
- **Runtime errors surface in Sentry** with actor context — on-call sees
  who was affected and which tenant they belong to.
- **Zero regression cost.** The full unit suite (664 tests) and full E2E
  suite (100 tests, 91 pre-existing + 9 new) are green.

### Negative / trade-offs

- **No cross-tenant "impersonate".** SUPER_ADMIN cannot browse another
  tenant's data as if they were a member. Deferred to a later ADR because
  the audit-trail story for impersonation is nontrivial (the `AuditLog`
  actor row would show SUPER_ADMIN, not the tenant user — that's correct
  but requires a UI marker so HR doesn't get confused).
- **Bootstrap forces an HR user.** Callers cannot create an empty tenant
  and back-fill users later. Rejected the alternative because an empty
  tenant is unusable (no one can log in to configure it) and the wire
  contract is simpler when both requirements ship together.
- **Pino output changes are visible.** Anyone parsing logs by eye will see
  JSON in production instead of Nest's `[ContextName] message`. Pretty
  mode is one env flag away.
- **Sentry adds ~5 MB to `node_modules`.** OTel instrumentation drags in
  a lot of transitively-installed packages; measured but accepted.

## Alternatives considered

- **Single `/admin/companies` for both singular + plural.** Rejected —
  encoding "who am I allowed to touch" in the path prevents entire classes
  of guard mistakes.
- **Winston instead of pino.** Pino benchmarks ~2× faster at JSON emit,
  and `nestjs-pino` has a smaller surface (single module, no formatter
  zoo). Winston's popularity edge was not worth the perf hit under the
  E2E test load.
- **OpenTelemetry SDK directly, without Sentry.** Fine for tracing, but
  we also want error grouping, release tagging, and per-user context out
  of the box. Sentry's Nest integration already ships those; rolling our
  own on top of OTel would be weeks of work for the same outcome.

## Frontend surface (Fase 29b)

The `/admin/companies` route at `apps/web/app/(dashboard)/admin/companies/`
ships alongside the API and reuses the same infrastructure as the User
Admin flow so the operator gets a familiar shape:

- **Subnav filter.** `admin-subnav.tsx` filters tabs by role — the "Tenant"
  tab is hidden for HR, but the `<RequireRole roles={['SUPER_ADMIN']}>`
  guard on the page still runs so HR who bookmarks the URL sees the
  standard 403 panel instead of a broken screen.
- **Shared credential-reveal.** The bootstrap response's `temporaryPassword`
  is surfaced via the existing `<CredentialReveal>` component, which
  already handles mask/reveal, one-click copy, and the "one-time, cannot
  be recovered" copy. This matches the ergonomics HR already knows from
  reset-password on `/admin/users`.
- **Zod schemas colocated with the API DTOs.** `packages/shared-types/src/company-admin.ts`
  exports the create/update/list schemas the API DTOs mirror, and the
  form components use `zodResolver` directly. This makes the wire
  contract inspectable from a single file and blocks drift when we
  version the API.
- **Empty-string tolerance.** The optional-slug field of the create form
  is preprocessed to map `""` → `undefined` before `.optional()` runs,
  because react-hook-form emits empty strings from untouched inputs
  which would otherwise fail `.min(2)`.

The FE never persists the temp password in local/session storage, and
the mutation's `onSuccess` handler is the only place it is held —
component state is cleared when the reveal panel is dismissed.

## Verification

- **Unit** — `apps/api/src/company-admin/company-admin.service.spec.ts`
  (RBAC gate for every method, bootstrap correctness, slug/email uniqueness,
  self-delete refusal, active-user guardrail) + `slug.spec.ts` (derivation
  - uniqueness bumping). 37 tests, all green.
- **E2E API** — `apps/e2e/tests/company-admin.spec.ts`. 9 tests:
  lifecycle, duplicate slug, duplicate email, invalid timezone, self-delete
  refusal, RBAC for HR/SUPERVISOR/EMPLOYEE (each hits every endpoint),
  unauthenticated. All green.
- **E2E UI** — `apps/e2e/tests/company-admin-ui.spec.ts`. 4 tests:
  SUPER_ADMIN create → reveal → edit → guarded delete happy path;
  own-tenant delete disabled; HR does not see the "Tenant" tab; HR
  direct navigation shows the access-denied panel. All green.
- **Full suite regression** — 664 unit tests + 104 E2E tests, all green.
